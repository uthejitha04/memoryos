# MemoryOS readiness audit — 2026-09-08

Verdict: the local recording/transcription core works, but the application is not ready to rely on as an everyday Omi companion. No application code was changed during this audit.

## Verified on this computer

- Started the Python server on port 18090 with isolated data under `C:\Projects\.tmp\memoryos-audit`, local transcription, and automatic polish disabled.
- The cached Whisper `small` model loaded successfully on CPU.
- Streamed the repository's synthetic speech fixture through the real audio WebSocket. The server saved a 14.5-second WAV including trailing silence and transcribed the expected “quick brown fox,” “coffee shop,” and “project roadmap” phrases.
- Inspected the rendered Live, Memories, recording-detail, and Ask views. The desktop layout is clean and readable; saved audio controls and transcript downloads are present. This was a desktop browser inspection, not a native Android or iPhone test.

## Findings

Test result: **88 passed, 1 failed, 2 skipped** in 317.75 seconds. Ran the complete `tests` directory with `HF_HUB_OFFLINE=1` and isolated temporary data. The real Whisper streaming test passed. The real polish test failed because `distil-large-v3` is not cached; it waited its full 300-second deadline after the model-loading error. The real embeddings and speaker-label checks were skipped because their dependencies are absent. Cloud provider tests use mocks, so these passes do not establish live provider availability. A recovery-thread warning also occurred during test fixture teardown; this was not established as a normal-startup production failure.

The test runner (`pytest`) was installed into the existing virtual environment for this audit. Initial sandbox attempts failed on temporary-folder permissions; the final run completed outside that restriction. Saved audio and transcript download endpoints returned 200, and keyword search found the synthetic recording.

### P1 — Desktop Connect Omi is not wired for Electron

`static/index.html:440` uses `navigator.bluetooth.requestDevice()` and the click handler at line 495 does not call the Python `/omi/connect` endpoint. `desktop/main.js` has no `select-bluetooth-device` handler. Electron cancels Bluetooth requests without that handler. The request failure is silently caught by the page, so the button can appear to do nothing.

Fix either the Electron device picker or route the desktop UI to the existing Python BLE client. The desktop dependencies are also not installed in the current `desktop` directory.

Source: https://www.electronjs.org/docs/latest/api/web-contents#event-select-bluetooth-device

### P1 — Fragmented Opus packets use the wrong reassembly assumption

`omi_transcribe.py:48` and `static/index.html:426` group fragments by an unchanged packet number and ignore the fragment index. Omi's published protocol shows the notification packet counter incrementing between fragments, with the index indicating fragment position.

The existing `tests/test_opus.py` generates fragments with the same packet number, so it validates the implementation's assumption. A separate synthetic check incremented notification numbers while preserving fragment indexes: one second of source audio produced 2.3015 seconds of corrupt output and 138 decoder errors; the existing test framing produced 0.979 seconds. Unfragmented frames may work, but fragmented audio is not reliable. Actual device firmware still needs verification.

Source: https://docs.omi.me/doc/developer/Protocol

### P1 — Memory features are unavailable in the current installation

`requirements.txt` omits `sentence-transformers`; it is absent from the virtual environment. `server.py:1313` therefore leaves the memory engine disabled. Semantic search, Ask, and automatic memory enrichment cannot operate. The Dockerfile installs the package separately, so local and cloud setup differ.

The UI still advertises Ask without explaining this limitation until the user submits a question. Dependency installation and a startup capability check are needed.

### P1 — Connection loss can silently lose audio

The browser Omi stream sends only while its WebSocket is open and installs no ongoing close/error recovery handler. The Android service logs WebSocket failure but keeps capturing, ignores the result of `send()`, and has no local recording buffer or retry queue. The Python BLE client exits when the pendant disconnects, without reconnecting.

Provide visible recording failure state, reconnect with backoff, and durable local buffering before relying on all-day capture.

### P2 — Multiple recording sources share one session

`server.py:1264` accepts every audio socket into the same global Hub, overwriting `source` with `mic`. There is no exclusive capture owner. Browser Omi audio also uses this route. A second tab or concurrent microphone recording can interleave audio; closing one stream can end the shared session while another continues.

### P2 — The browser's 8 kHz PCM path forwards the wrong rate

`static/index.html:430` forwards codec 1 PCM unchanged, but `/ws/audio` interprets every sample stream as 16 kHz. An 8 kHz device would play/transcribe at the wrong speed. Resample or reject that codec explicitly. The Python decoder does upsample this case.

### P2 — Phone companion is incomplete

The Android native service supports standard microphone/headset capture, not Omi BLE GATT audio. Its WebView shell is not a substitute for a native Omi connection. The app also hardcodes a Railway URL with no normal server-address setup UI. The hosted deployment was not tested.

### P2 — Higher-quality offline polish is not provisioned

The `small` live model is cached, but `distil-large-v3` is not. Local polish needs a first-use model download and cannot currently run offline. Speaker-label dependencies are also absent. The UI should distinguish these optional capabilities from ready features.

## Recommended repair order

1. Make one desktop Omi connection path work reliably and fix packet framing, codec handling, and error reporting.
2. Restore memory dependencies and verify index/search/Ask using actual embeddings.
3. Enforce one capture owner and add reconnect/buffering.
4. Test a real pendant recording, playback, transcription, disconnect/reconnect, and a longer session.
5. Finish native phone Omi capture and background behavior.

Passing synthetic/backend tests cannot replace the live pendant test. This audit did not flash firmware, record ambient conversations, or alter existing recordings.
